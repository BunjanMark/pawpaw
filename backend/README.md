# PawPaw Backend

ASP.NET Core 10 backend using an Ardalis Clean Architecture adaptation.

## Projects

- `PawPaw.Core` — domain entities and domain rules.
- `PawPaw.UseCases` — application use cases, validation, and ports.
- `PawPaw.Infrastructure` — EF Core/PostgreSQL and external-service implementations.
- `PawPaw.Web` — HTTP endpoints, authorization policies, middleware, OpenAPI, rate limiting, and composition root.

Tests are split into unit, integration, and functional projects.

## Local development

Requirements: .NET 10 SDK and PostgreSQL 17+ (or Docker).

1. Start PostgreSQL only if desired:

   ```bash
   cp .env.example .env
   # Set a local-only POSTGRES_PASSWORD in .env
   docker compose up -d postgres
   ```

2. Configure the API connection string with .NET user secrets:

   ```bash
   cd backend
   dotnet user-secrets set --project src/PawPaw.Web/PawPaw.Web.csproj \
     "ConnectionStrings:DefaultConnection" \
     "Host=localhost;Port=5432;Database=pawpaw;Username=pawpaw;Password=YOUR_LOCAL_PASSWORD"
   ```

3. Run the API:

   ```bash
   dotnet run --project src/PawPaw.Web/PawPaw.Web.csproj
   ```

Operational health is exposed at `/health`. API routes use the `/api/v1` prefix.

## Configuration and secrets

`appsettings.json` and environment-specific appsettings files are intentionally ignored. `src/PawPaw.Web/appsettings.example.json` documents safe configuration keys only. Use `dotnet user-secrets` locally and environment variables or the deployment provider's secret manager in hosted environments.

YAML is not globally ignored because Compose and CI workflows must be versioned. Only local/secret YAML patterns are ignored.

## EF Core migrations

Migrations are committed to Git. Generate them from the repository after a domain/schema change has been reviewed:

```bash
dotnet ef migrations add <MigrationName> \
  --project src/PawPaw.Infrastructure/PawPaw.Infrastructure.csproj \
  --startup-project src/PawPaw.Web/PawPaw.Web.csproj \
  --context AppDbContext \
  --output-dir Data/Migrations
```

Then apply locally with:

```bash
dotnet ef database update \
  --project src/PawPaw.Infrastructure/PawPaw.Infrastructure.csproj \
  --startup-project src/PawPaw.Web/PawPaw.Web.csproj \
  --context AppDbContext
```

The initial migration is intentionally not hand-authored in this bootstrap; it should be generated by EF after the first schema review.

## Storage

Development uses `IFileStorage` with a local filesystem implementation. Business/application code does not depend on the storage provider, allowing a later Cloudinary, Supabase Storage, S3, or Azure Blob implementation without changing use cases.

## Authentication

Authentication mechanics are intentionally deferred. The Web project already owns centralized authorization policy names and authorization registration, so JWT/Identity/OAuth can be introduced later without moving authentication concerns into Core.
